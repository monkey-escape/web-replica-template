# 优化图格式协商与稳定抓图

- date: 2026-11-22

公开目标站按 SSR DOM 和公开 CSS 重建成可维护的分段源（共享 chrome 与各页 section），运行时仍是 Vite+ 多页应用。图片、字体和视频走本地 `/media/<site-id>/...`，公开 JSON 走 `/api/mock/...`。

循环在感知阈值下全部通过，状态 `ready_for_review`。下面是这轮真正失败过、下次应避开的点。

## 真实失败

1. **参考图拍在 CSS 过渡中间。** 本地页面没有网络延迟，按钮背景和表单边框从 UA 默认样式过渡到品牌色时就被截图；IntersectionObserver 驱动的 reveal 类也还没稳定。清空旧参考图后，多个桌面和移动路由的分数都会偏掉。应在拉高视口后等待 `document.images` 完成解码，再额外等至少 1 秒，并给克隆侧固定动画终态。
2. **`next/image` 的格式协商。** 用 Node 默认 `Accept: */*` 下载优化图得到 JPEG 或 PNG，而参考图里的浏览器拿到的是 WebP 或 AVIF。源文件尺寸一致，图片区域仍可能有几百到几千个像素差。应使用浏览器 `Accept` 下载，按实际 content-type 存为 `.webp` / `.avif`，并同步改掉 `srcset` 和 `src`。
3. **共享顶栏的 CSS 动画让不同路由或视口拍到不同状态。** 顶栏用 keyframes 轮播两条促销或物流文案时，逐页截图会落在不同相位，出现大面积像素差。应把共享组件的静态参考态按路由固定下来，或在抓图辅助里显式暂停动画；不要靠加载时间碰运气。
4. **桌面和手机不是同一套 DOM。** 目标站常常为两个视口准备两套节点。同一个 `data-component` 不能同时挂在两套上；用视口专用属性在加载时只挂可见节点，结构测量才能按视口对齐。
5. **测量代码把目标选择器用在克隆上。** `sections.json` 的 `targetSelector` 若被优先拿到克隆 DOM 上查询，会出现大量 missing styles；目标页的超长 section 也可能被高度过滤器误拒。目标选择器和克隆选择器必须分开。

## 对应陷阱

见 `docs/experience/traps.md` 中的 `trap-0001` 到 `trap-0003`、`trap-0008`、`trap-0009`。
